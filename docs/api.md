# API Reference

Base URL: `http://localhost:8000`

Interactive documentation is generated by FastAPI and is the authoritative
schema:

- Swagger UI: `http://localhost:8000/api/docs`
- ReDoc: `http://localhost:8000/api/redoc`
- OpenAPI JSON: `http://localhost:8000/api/openapi.json`

The TypeScript types in `frontend/lib/types.ts` mirror these schemas.

> **Research prototype.** Every finding returned by this API is a model-derived
> research estimate requiring review by a qualified radiologist. The API does not
> provide a clinical diagnosis and is not a medical device.

---

## Error format

Every failure, at every status code, returns the same envelope. A Python
traceback is never included; unexpected errors carry a `reference` that maps to a
server-side log entry.

```json
{
  "error": {
    "code": "UNREADABLE_VOLUME",
    "message": "Unable to read the MRI volume. The file may be corrupt, truncated, or not a supported image volume.",
    "details": { "reader_error": "RuntimeError" }
  }
}
```

### Error codes

| Code | Status | Meaning |
| --- | --- | --- |
| `UNSUPPORTED_FORMAT` | 400 | Extension is not one of `.mha`, `.mhd`, `.nii`, `.nii.gz` |
| `FILE_TOO_SMALL` | 400 | Below 2 KB, cannot be a volume |
| `FILE_TOO_LARGE` | 400 / 413 | Above the 300 MB limit |
| `UNREADABLE_VOLUME` | 400 | SimpleITK could not read the file |
| `UNEXPECTED_DIMENSIONS` | 400 | Not 3-D, or in-plane size outside 64–4096 px |
| `UNEXPECTED_SLICE_COUNT` | 400 | Sagittal slices outside 3–512 |
| `IMPLAUSIBLE_SPACING` | 400 | In-plane pixel spacing not plausible for lumbar MRI |
| `EMPTY_VOLUME` | 400 | No finite voxel values |
| `ANALYSIS_NOT_FOUND` | 404 | Unknown analysis id |
| `SLICE_OUT_OF_RANGE` | 404 | Slice index outside the study |
| `RESULT_NOT_READY` | 409 | Analysis has not completed |
| `SLICES_NOT_READY` | 409 | Slice images not rendered yet |
| `ANALYSIS_FAILED` | 409 | Analysis failed; no result exists |
| `ANALYSIS_TIMEOUT` | — | Reported inside a status response |
| `ANALYSIS_INTERRUPTED` | — | Server restarted mid-analysis; start it again |
| `UPLOAD_MISSING` | 410 | The stored upload is gone |
| `INVALID_REQUEST` | 422 | Malformed request body or query |
| `MODEL_UNAVAILABLE` | 503 | Checkpoint not loaded; check `MODEL_CHECKPOINT` |
| `INTERNAL_ERROR` | 500 | Unexpected failure, with a log `reference` |

## `POST /api/analysis/upload`

`multipart/form-data` with a single `file` field. The file is written to disk,
then validated: extension, size, readability, dimensionality, slice count and
pixel spacing. A rejected upload is deleted and no analysis is created.

```bash
curl -F "file=@data/extracted/images/33_t2.mha" \
  http://localhost:8000/api/analysis/upload
```

**201 Created**

```json
{
  "analysis_id": "56bf0a10300fd3cd",
  "status": "queued",
  "study": {
    "filename": "33_t2.mha",
    "size_bytes": 1268000,
    "format": ".mha",
    "modality": "t2",
    "modality_source": "filename_heuristic",
    "slice_count": 24,
    "dimensions": [242, 305],
    "in_plane_spacing_mm": [1.0982, 0.866],
    "slice_spacing_mm": 4.6731,
    "native_orientation": "LPS"
  },
  "created_at": "2026-09-24T20:00:00Z",
  "message": "Upload validated. Start the analysis to process this study."
}
```

Notes:

- `analysis_id` is a random 16-character hex token. It is never derived from the
  filename, so no identifying information appears in a URL.
- Filenames are sanitised to their basename and a conservative character set.
- `modality_source` is honest about provenance: a converted `.mha` carries no
  DICOM series description, so the modality is usually a filename heuristic.

## `POST /api/analysis/{analysis_id}/run`

Queues the analysis and returns immediately. The pipeline runs on a background
worker.

**202 Accepted**

```json
{ "analysis_id": "56bf0a10300fd3cd", "status": "queued" }
```

Calling `run` on an already-running analysis is safe and returns its current
status. Calling it on a completed analysis returns `completed` without redoing
the work.

## `GET /api/analysis/{analysis_id}/status`

Poll this while a job runs. Progress comes from real pipeline stage boundaries
and is monotonic.

```json
{
  "analysis_id": "56bf0a10300fd3cd",
  "status": "processing",
  "progress": 62,
  "stage": "Disc indexing",
  "stages_completed": ["Upload validated", "Preprocessing", "Segmentation"],
  "elapsed_seconds": 2.4,
  "started_at": "2026-09-24T20:00:01Z",
  "finished_at": null,
  "error": null
}
```

States: `queued` → `processing` → `completed` | `failed`.

Stage progression: `Upload validated` 0 → `Loading MRI` 10 → `Preprocessing` 20 →
`Segmentation` 40 → `Disc indexing` 60 → `Feature extraction` 75 →
`Radiological analysis` 90 → `Complete` 100.

On failure, `error` carries the envelope contents:

```json
{
  "status": "failed",
  "error": {
    "code": "ANALYSIS_FAILED",
    "message": "Analysis failed during segmentation.",
    "details": { "stage": "Segmentation", "error_type": "RuntimeError" }
  }
}
```

### Field semantics that matter

| Field | Meaning |
| --- | --- |
| `discs[].index` | Integer disc position, 1 = most inferior. **Not** an anatomical level name; the dataset does not state which vertebra is L5. |
| `identity_confidence` | Fraction of the series' slices supporting this disc's series-level track. Describes cross-slice tracking consistency, **not** clinical certainty. |
| `modic_type` | **Always `null`.** Only binary "any Modic change" was modelled. |
| `spondylolisthesis` | **Always `null`.** Five positive test cases is too few to validate. |
| `pfirrmann_grade` | `null` on a non-T2 study; the grade is defined on T2 signal, so it is withheld rather than extrapolated. |
| `findings[].strength` | How well that target validated: `strong`, `moderate`, `modest`, `weak`. |
| `timepoint` | Always a single `baseline`. The seam for a future longitudinal module. |
| `validated_metrics` | Measured on a 33-patient held-out test split, **not** on the uploaded study. |

Any field that cannot be computed is `null` with an `unavailable_reason`. No value
is ever fabricated.

## `GET /api/analysis/{analysis_id}/slice/{slice_id}`

Returns one rendered slice as a PNG. `slice_id` is the zero-based slice index.
The volume itself is never transferred.

| Query | Default | Description |
| --- | --- | --- |
| `mode` | `overlay` | `original`, `mask` or `overlay` |
| `opacity` | `0.45` | Overlay alpha, 0–1 |
| `classes` | `1,2,3` | Class ids to draw: 1 vertebra, 2 disc, 3 canal |
| `scale` | `1` | Integer upscale, 1–3 |

```bash
curl -o slice12.png \
  "http://localhost:8000/api/analysis/56bf0a10300fd3cd/slice/12?mode=overlay&opacity=0.5&classes=2,3"
```

Response headers include `X-Slice-Count` and
`Cache-Control: public, max-age=86400, immutable` — a completed analysis's slices
never change, so the browser may cache them indefinitely.

Class filtering is applied server-side, so a hidden class is not transmitted.

## `GET /api/analysis/{analysis_id}/report`

Same payload as `/result`. Kept as a separate route for the report view so a
future report-specific projection can diverge without breaking the results
screen.

---

## `GET /api/analysis/{analysis_id}/download`

| Query | Default | Description |
| --- | --- | --- |
| `fmt` | `md` | `md` for Markdown, `json` for the raw result |

Returns `Content-Disposition: attachment`. The Markdown report has eight
sections: study information, processing information, segmentation overview,
disc-level analysis, quantitative measurements, model-derived findings,
limitations, and the research disclaimer. It is assembled from deterministic
templates filled with measured values — no language model is involved.

## `DELETE /api/analysis/{analysis_id}`

Removes the upload, the result and the cached slice arrays.

```json
{ "analysis_id": "56bf0a10300fd3cd", "deleted": true }
```

## Typical sequence

```bash
BASE=http://localhost:8000

# 1. confirm the model is loaded
curl -s $BASE/api/health | python -m json.tool

# 2. upload
ID=$(curl -s -F "file=@data/extracted/images/33_t2.mha" \
  $BASE/api/analysis/upload | python -c "import json,sys;print(json.load(sys.stdin)['analysis_id'])")

# 3. start
curl -s -X POST $BASE/api/analysis/$ID/run

# 4. poll
curl -s $BASE/api/analysis/$ID/status

# 5. result
curl -s $BASE/api/analysis/$ID/result | python -m json.tool

# 6. a slice
curl -s -o slice.png "$BASE/api/analysis/$ID/slice/12?mode=overlay"

# 7. report
curl -s -o report.md "$BASE/api/analysis/$ID/download?fmt=md"
```
